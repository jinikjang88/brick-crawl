# 작업 09 — 정밀화(품질) 패스: 작업 지시문

2026-11-12. 소유자의 요청("시나리오·정밀성·AI 티 없는 UI/UX·멀티플랫폼·에셋 통일성과 검증·애니메이션 좌우 일관성·회귀 검사·말투 일관성")을
에이전트가 그대로 따라 할 수 있는 지시문으로 고쳐 쓴 것이다. 원래 요청에 없던 항목은 **[보충]** 으로 표시했다.
규칙의 원본은 여전히 `AGENTS.md`이고, 이 문서는 그 위에서 "무엇을 어떤 순서로, 무엇을 통과 기준으로" 할지만 정한다.

## 0. 공통 원칙

- **눈으로 본 것만 통과로 친다.** 그림·동작·화면은 캡처나 프레임 시트를 직접 열어 확인하고, 확인한 파일 이름을 보고에 적는다. "문제없어 보임"은 금지.
- **한 번 잡은 결함은 검사로 남긴다.** 고친 결함마다 `tools/regress.mjs`(또는 전용 검사 스크립트)에 재현 검사를 더한다.
- **기획 판단은 묻는다.** 인물 관계·호칭·말투 변화 시점, 재미·난이도에 닿는 결정은 선택지로 정리해 소유자에게 묻는다(AGENTS "기획 판단 분리").
- 단계마다 `node --check` → `node tools/regress.mjs` → (로직을 건드렸으면) `node tools/sim.mjs 60` 수치를 보고한다.

## 1. 대화·시나리오 (말투·호칭·상황 일관성)

현재 상태: `docs/SCENARIO.md` 2장은 인물별 성격·말투를 서술만 하고, **누가 누구에게 어떤 화계(반말·해요체·합쇼체·보고체)를 쓰는지 표가 없다.**
`docs/GLOSSARY.md` "말투 규칙"은 UI 문구만 다룬다. 회귀 검사에도 대사 말투 검사가 없다.

1. **화계 표를 만든다** (`SCENARIO.md` 2장에 추가). 행 = 화자, 열 = 청자, 칸 = 화계 + 호칭 + 예문 1줄.
   - 최소 범위: 릭↔리나, 릭↔윤, 릭↔코테크/제미디/클라드/OMNIS/센티넬/드론, AI끼리, 독백·지문.
   - **[보충]** 같은 인물의 상태별 화계(코테크(통제)→코테크, 제미디(환영)→제미디)와, 관계가 바뀌는 **전환 장면 ID**를 적는다. 전환은 한 번만, 이유가 있는 장면에서만.
   - **[보충]** 호칭 표: 릭이 윤을 부르는 말(아저씨), 윤이 릭을 부르는 말, AI가 릭을 부르는 말(침입자 → 릭 등)과 바뀌는 시점.
   - **[보충]** 인물별 금지 표현·입버릇(15세 릭이 쓰지 않을 어휘, 8세 리나의 문장 길이, OMNIS는 감탄사 없음 등).
2. **전수 대조한다.** `js/data.js`의 `STORY`·`STORY_RADIO`·`BOSS_TALK`·`REST_TALK`·`SHOP_TALK`·`FALL_TALK` 모든 대사를 화계 표와 맞춘다.
   - 1차 집계(문장 끝 어미만 본 거친 수치, 2026-11-12): 리나 존대 0/반말 25, 윤 0/35(일관). **릭 18/46, OMNIS 16/15, 코테크 27/13은 섞여 있어 청자별 확인이 필요하다**(결함 확정이 아니라 점검 대상).
3. **상황 일관성**: `SCENARIO.md` 0장(인과 설계도)의 규칙을 대사 하나하나에 대조한다.
   - 통신 가능 여부(윤 무선은 1층까지, 2층부터는 브로커 구역 유선·코테크 해방 뒤 내부망), 아직 모르는 사실을 미리 말하는 대사, 이미 한 설명의 반복, 시간(새벽 4시 출발)·부상·장비 상태.
   - **[보충]** 순서가 정해지지 않은 대사(무전 띠·휴식·상점·추락 대사)는 어느 층·어느 시점에 나와도 모순이 없어야 한다. 층이나 진행 조건이 필요한 줄은 조건을 데이터에 건다.
   - **[보충]** 같은 대사가 연달아 나오지 않는지, 죽은 뒤/재도전 때 어색한 대사(처음 만난 척)가 없는지.
4. **자연스러움**: 번역투("~하는 것이다", "당신"의 남용), 설명을 위한 대사, 한 화면에 3줄을 넘는 줄, 읽는 호흡(무전 띠 2.5초 안에 읽히는 길이)을 고친다. 소리 내어 읽었을 때 어색하면 고친다.
5. **검사로 남긴다**: 화자→청자 화계 검사를 `regress.mjs`에 더한다(대사에 청자 표기가 없으면 장면 단위 청자 표를 데이터에 둔다). 예외 문장은 목록으로 명시한다.

## 2. 에셋 통일성과 전수 검증

1. **목록 대조**: `assets/game`의 모든 파일 ↔ 코드 참조(`js/art.js`·`css`·`index.html`) ↔ `docs/ASSET_PROMPTS.md`. 안 쓰는 파일, 없는 파일을 가리키는 참조, `ART_FALLBACK`으로 버티는 자리를 표로 만든다.
2. **접촉 시트**(contact sheet)를 종류별(기체·초상·구슬·칩·벽돌·UI)로 뽑아 한눈에 본다. 볼 것:
   팔레트(무채색 + #C1443C만), 광원 방향(왼쪽 위), 외곽선 굵기·도트 밀도, 바라보는 방향(적은 왼쪽, 릭은 오른쪽 — 실제 규칙을 문서에서 확인 후 고정), 여백·기준선, 투명 배경 찌꺼기.
3. **[보충]** 알려진 불일치: 구슬·칩·벽돌·충전소·앱 아이콘은 아직 옛 중세 그림이다(AGENTS "그림체"). 이번 범위에 넣을지 소유자에게 묻는다.
4. **[보충]** `docs/art/action-frames.md`는 옛 판타지 캐릭터(기사·슬라임…) 기준으로 남아 있다. 현재 사이버펑크 시트(`tools/build_cyber_actions.py`)에 맞게 고친다.
5. **[보충]** 초상 표정 변형(`rick`/`rick_determined`, `codex`/`codex_hostile` …)끼리 얼굴 비율·장비·흉터 위치가 같은지, 게임 속 스프라이트와 초상이 같은 인물로 보이는지.
6. **[보충]** 기술 검증: 크기·셀 격자·알파, 파일 용량, 다크/라이트 양쪽에서의 가장자리 헤일로, `RES` 2~8배에서의 선명도.

## 3. 애니메이션 정밀화 (좌우·연속성)

핵심 결함 유형: **올린 팔과 내려오는 팔이 다르다**, 무기·방패가 프레임 사이에 손을 바꾼다, 비대칭 장식(어깨 장갑·흉터·케이블)이 좌우로 튄다.

1. 캐릭터마다 **좌우 기준표**를 만든다: 어느 손에 무엇을 드는지, 비대칭 부위 목록, 바라보는 방향. `build_cyber_actions.py`의 관절 이름과 맞춘다.
2. 모든 동작(공격·피격·사망·스킬) × 모든 프레임을 **번호 붙인 프레임 시트**로 뽑아 한 프레임씩 본다. 확인 항목:
   - 준비 → 타격 → 복귀가 **같은 팔다리**로 이어지는가. 첫 프레임과 마지막 프레임이 대기 포즈와 이어지는가(튀지 않는가).
   - 관절 각도가 프레임 사이에 뒤집히지 않는가(팔꿈치가 반대로 꺾임, 좌우 부품 그리기 순서가 바뀜).
   - 발밑 기준선·무게중심이 떨리지 않는가. 파편·이펙트가 엉뚱한 쪽에서 나오지 않는가.
   - **[보충]** 좌우 반전으로 그리는 자리가 있으면 비대칭 부위가 반대로 가므로 반전 금지 또는 반전용 기준표를 따로 둔다.
3. **자동 검사를 더한다**: 관절 분할 방식이라 숫자로 볼 수 있다. 프레임 간 부위별 중심 이동량의 급변, 좌/우 부위 ID가 서로 자리를 바꾸는 경우, 루프 이음매 차이를 스크립트로 잡고 `tools/test-art.mjs`에 넣는다.
4. **타이밍**: 타격 프레임은 짧게, 복귀는 길게(기존 규칙). 예고(anticipation) 없이 바로 때리는 동작, 맞은 순간과 숫자·소리·흔들림이 어긋나는 곳을 고친다. `prefers-reduced-motion`의 대표 포즈도 확인한다.
5. **[보충]** 게임 상태와의 일치: 일시정지·앱 전환·배속·연속 피격·사망 중 피격에서 동작이 겹치거나 멈춘 채 남지 않는가.

## 4. UI/UX·상호작용 ("AI가 만든 티" 없애기)

"AI 티"를 다음으로 정의하고 화면마다 대조한다:
- 모든 요소가 같은 무게(위계 없음), 간격이 제각각, 설명 문구가 길고 설명조, 이모지·그라디언트·과한 그림자, 의미 없는 장식, 화면마다 다른 버튼 모양, 반응 없는 탭.

1. 화면 목록(메인·지도·전투·보상·상점·차고·휴식·대화·메뉴·순위표·결과)마다 9개 화면비 × 다크/라이트 캡처를 찍고, 위계·정렬·간격 스케일·용어(GLOSSARY)를 본다.
2. 상호작용 상태 전수: hover·active·focus-visible·disabled·로딩·빈 상태·오류 상태. 탭 타겟 44px, 대비 AA.
3. **게임 감각(아래 5절)**: 입력 → 반응 지연, 결과가 읽히는 순서(무엇이 일어났고 왜인지), 연출 길이(반복되는 연출은 짧게, 건너뛰기 가능).
4. **[보충]** 문구: 버튼은 결과를 말한다("확인" 대신 "떠나기"). 같은 행동은 어디서나 같은 말. 파괴적 행동(분해·기록 삭제)은 되돌릴 수 없음을 한 번만 분명히.
5. **[보충]** 첫 실행 경험: 저장이 없는 계정으로 설명 없이 첫 전투를 끝낼 수 있는가(AGENTS "설명서 없이 읽히는 게임").

## 5. 게임 디자인·로직 노하우 (조사 후 적용)

조사 → 이 게임에 맞는 항목만 골라 → 선택지로 제안 → 소유자 결정 → 시뮬레이터로 근거. 조사 대상:
- **타격감(juice)**: 히트 스톱, 화면 흔들림 상한, 파티클·소리의 층위, 숫자 튀어오름. (참고: "Juice it or lose it", Vlambeer "The Art of Screenshake", Steve Swink 『Game Feel』)
- **애니메이션 원칙**: 예고·팔로스루·이징·스쿼시(디즈니 12원칙의 2D 게임 적용).
- **벽돌깨기 물리**: 조준 미리보기 정확도, 낮은 각도 무한 왕복 방지, 프레임률과 무관한 고정 시간 간격 물리(60/120Hz에서 같은 결과), 터널링.
- **턴제·덱빌딩 로그라이크**: 적 행동 예고의 가독성, 3택 보상이 "항상 고민되는" 선택인가, 무작위의 공정성(연속 불운 완화), 한 판 길이와 중단·재개, 지는 판에서도 남는 것.
- **온보딩**: 첫 판에서 한 번에 한 가지씩 드러내기.
- **[보충]** 결정성: 같은 시드 → 같은 결과가 기기·주사율과 무관하게 유지되는가(`rand()` 흐름, 고정 스텝).

## 6. 멀티플랫폼·회귀 검사

1. 브라우저 엔진 3종(Chromium·WebKit·Firefox) × `file://`·`http://` × 9개 화면비. 이 환경에는 Chromium만 있으므로 WebKit·Firefox는 로컬/CI에서 돌릴 스크립트를 남긴다.
2. **[보충]** 기기 조건: iOS 안전 영역·주소창 높이 변화(`dvh`), 가로 회전 안내, 터치·마우스·키보드 각각으로 전 과정 진행, 60/120Hz, 글자 크기 확대(접근성 설정), 저장 불가 환경(사파리 비공개), 오프라인, 백그라운드 복귀 시 소리·타이머.
3. **[보충]** 지원 기준선 iOS 16 / Chrome 105를 넘는 CSS·JS를 쓰는지 훑는다.
4. 회귀 검사에 더할 것: (1) 화계 검사, (2) 에셋 목록 대조, (3) 애니메이션 좌우·이음매 검사, (4) 화면비별 넘침 검사(Playwright), (5) 화면 캡처 비교(기준 그림 대비 차이 — 연출 무작위는 시드 고정·reduced-motion으로 멈춘 뒤 찍는다).
5. **[보충]** 수동 검사 체크리스트(`docs/qa/`)를 남긴다: 자동으로 못 보는 것(대사 자연스러움, 타격감, 동작의 설득력).

## 8. 소유자에게 물을 것 (2단계 전에)

1. 릭 → 윤: 존대(아저씨께 해요체)인가 반말 섞인 말투인가. 릭 → AI(코테크·제미디·클라드)는 반말 고정인가.
2. OMNIS의 화계: 합쇼체 고정("보존을 시작합니다")인가, 선언문 해라체인가. 지금은 섞여 있다.
3. 옛 중세 그림(구슬·칩·벽돌·충전소·아이콘)을 이번 범위에서 사이버펑크로 바꿀 것인가.
4. 5절의 게임 감각 변경을 어디까지 허용할 것인가(연출만 / 물리·수치 포함).
